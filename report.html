Parte 1 · Refresh Tokens y Rate Limiting (01-local)

1.1 Arquitectura de Refresh Tokens con Rotación Estricta

En arquitecturas modernas basadas en JSON Web Tokens (JWT), los Access Tokens poseen una vida útil intencionalmente corta (en nuestra implementación, 15 minutos) para minimizar el impacto de una posible interceptación. Sin embargo, exigir que el usuario ingrese sus credenciales repetidamente degradaría la experiencia. Para solventarlo de forma segura, se incorporaron Refresh Tokens con rotación automática y expiración a 7 días.

El refresh token se genera como una secuencia criptográficamente aleatoria de 32 bytes (256 bits de entropía) mediante RandomNumberGenerator.GetBytes(32). Siguiendo las directrices del NIST y OWASP, el valor original jamás se almacena en la base de datos; en su lugar, se computa y guarda su hash criptográfico SHA-256 (64 caracteres hexadecimales).

Entidad RefreshToken implementada en EF Core: Incluye Id, UserId, TokenHash, ExpiresAt, CreatedAt, RevokedAt (nullable) y ReplacedByTokenId (nullable para mantener la trazabilidad de rotación). 
// 01-local/Auth.Local.Api/Models/RefreshToken.cs
public class RefreshToken
{
    public int Id { get; set; }
    public int UserId { get; set; }
    public required string TokenHash { get; set; }
    public DateTime ExpiresAt { get; set; }
    public DateTime CreatedAt { get; set; }
    public DateTime? RevokedAt { get; set; }
    public int? ReplacedByTokenId { get; set; }
    public User? User { get; set; }
    public RefreshToken? ReplacedByToken { get; set; }
}

1.2 Detección de Reutilización (Reuse Detection)

La rotación de refresh tokens mitiga el riesgo de persistencia tras un robo de credenciales: cada vez que el cliente consume un refresh token para obtener un nuevo access token, el refresh token utilizado se marca inmediatamente como revocado (RevokedAt = DateTime.UtcNow) y se enlaza al nuevo token creado (ReplacedByTokenId).

Si un atacante y la víctima intentan utilizar el mismo token, se desencadena la detección de reutilización: al recibir una petición con un token que ya posee RevokedAt != null, el servidor asume de inmediato que la sesión ha sido comprometida. En respuesta, la API revoca automáticamente todos los refresh tokens activos de ese usuario y responde con código 401 Unauthorized, invalidando de inmediato el acceso en todos los dispositivos. 

// Extracto de POST /api/auth/refresh en AuthEndpoints.cs
if (token.RevokedAt is not null)
{
    // Detección de reutilización: revocar todas las sesiones del usuario afectado
    var activeTokens = await db.RefreshTokens
        .Where(r => r.UserId == token.UserId && r.RevokedAt == null)
        .ToListAsync();

    var now = DateTime.UtcNow;
    foreach (var active in activeTokens) active.RevokedAt = now;
    await db.SaveChangesAsync();

    return Results.Json(
        new { message = "Detección de reutilización: este refresh token ya fue revocado. Se revocaron todas las sesiones del usuario." },
        statusCode: StatusCodes.Status401Unauthorized);
}

1.3 Rate Limiting y Análisis del Endpoint 2FA Verify

Se configuró el middleware nativo AddRateLimiter de ASP.NET Core aplicando una ventana fija de 5 intentos por minuto por dirección IP para los endpoints POST /api/auth/login y POST /api/auth/2fa/verify, devolviendo el código estándar 429 Too Many Requests con la cabecera Retry-After.

Pregunta técnica requerida: ¿Por qué el endpoint POST /api/auth/2fa/verify requiere obligatoriamente rate limiting?
Un código de segundo factor TOTP (RFC 6238) consta de 6 dígitos decimales, lo que representa un espacio de búsqueda de únicamente 1,000,000 de combinaciones posibles (000000 a 999999). Si un atacante ya obtuvo las credenciales de primer factor (correo y contraseña) o interceptó el tempToken, podría orquestar un ataque de fuerza bruta distribuido enviando miles de peticiones HTTP por segundo. Debido a que el código TOTP tiene una ventana de validez de 30 segundos (más la tolerancia por desvío de reloj de 30 a 60 segundos adicionales), un script automatizado sin limitación de tasa podría probar el espacio completo en menos de un minuto. El rate limiting restringe drásticamente los intentos a solo 5 por minuto, reduciendo la probabilidad matemática de acierto por fuerza bruta a un despreciable 0.0005%, protegiendo eficazmente la cuenta.

1.4 Frontend: Renovación Automática Transparente (React)

En el frontend (auth-local-web), se adaptó el AuthContext para almacenar en memoria tanto el token de acceso como el refreshToken. Al invocarse authFetch:

  1. Se realiza la petición original con la cabecera Authorization: Bearer <token>.
  2. Si la API responde con 401 Unauthorized (token expirado tras 15 minutos), authFetch intercepta el error, retiene la petición y envía automáticamente una solicitud POST /api/auth/refresh con el refreshToken almacenado.
  3. Al recibir el nuevo par de tokens, actualiza el estado de la aplicación y reintenta la petición original una sola vez de forma completamente transparente para el usuario, sin interrupciones ni cierres de sesión.
  4. Si el refresh falla (por ejemplo, por expiración total o revocación), se ejecuta logout() limpiando el estado y redirigiendo al inicio de sesión.
  5. El botón «Cerrar sesión» de la barra de navegación invoca POST /api/auth/logout pasando el refresh token para revocarlo en la base de datos antes de limpiar la memoria del navegador.

Parte 2 · Roles y Permisos con Auth0 (02-auth0)

2.1 Configuración de Roles y Permisos RBAC en Auth0

En el panel de administración de Auth0 se configuró el esquema de control de acceso basado en roles (RBAC) para la API Demo Auth API (Identifier: https://api.demo-auth.local, algoritmo de firma: RS256):

  • Permisos definidos en la API:
    • read:messages: Lectura de recursos del sistema.
    • delete:messages: Eliminación de recursos de mensajería (operación privilegiada).
  • Opciones RBAC activadas: Se habilitaron las casillas «Enable RBAC» y «Add Permissions in the Access Token» para que Auth0 inyecte el claim permissions: [...] en el cuerpo del access token emitido.
  • Roles configurados:
    • Lector: Posee únicamente el permiso read:messages.
    • Administrador: Posee ambos permisos: read:messages y delete:messages.
  • Usuarios de prueba creados:
    • lector@demo.com asignado al rol Lector.
    • admin@demo.com asignado al rol Administrador.

2.2 Políticas en la Web API y Registro de Auditoría

En Auth.Auth0.Api/Program.cs se definieron las políticas de autorización correspondientes y el recurso en memoria Message con sus endpoints: 

// Políticas RBAC en Auth.Auth0.Api
builder.Services.AddAuthorizationBuilder()
    .AddPolicy("read:messages", policy => policy
        .RequireAuthenticatedUser()
        .RequireClaim("permissions", "read:messages"))
    .AddPolicy("delete:messages", policy => policy
        .RequireAuthenticatedUser()
        .RequireClaim("permissions", "delete:messages"));

// Endpoints de Mensajes con Logging del sub
app.MapGet("/api/messages", () => Results.Ok(messages))
    .RequireAuthorization("read:messages");

app.MapDelete("/api/messages/{id:int}", (int id, ClaimsPrincipal user, ILogger<Program> logger) =>
{
    var sub = user.FindFirstValue("sub") ?? "desconocido";
    var msg = messages.FirstOrDefault(m => m.Id == id);
    if (msg is null) return Results.NotFound(new { message = $"Mensaje {id} no existe." });

    messages.Remove(msg);
    // Registro explícito en consola de auditoría del usuario responsable:
    logger.LogInformation("MENSAJE ELIMINADO - Id: {MessageId}, Texto: '{Text}', Usuario Sub: {Sub}", id, msg.Text, sub);

    return Results.Ok(new { message = $"Mensaje {id} eliminado exitosamente.", deletedBy = sub });
})
.RequireAuthorization("delete:messages");

2.3 Frontend RBAC y Análisis Crítico de Seguridad

En auth0-web, el componente MessagesPanel.tsx decodifica el Access Token mediante decodeJwt() para examinar el arreglo permissions. Si el token no contiene el permiso delete:messages, el botón «Eliminar» se omite completamente del renderizado en pantalla.

Pregunta técnica requerida: ¿Por qué ocultar el botón en la interfaz de usuario no es suficiente como control de seguridad?
Ocultar componentes visuales en el cliente responde estrictamente a un principio de usabilidad (UX) y no de seguridad (constituye una falacia de seguridad por oscuridad). El navegador web es un entorno enteramente controlado por el usuario final o un adversario. Cualquier usuario con el rol de Lector puede abrir las herramientas de desarrollo (DevTools de Chrome/Edge), inspeccionar el almacenamiento de la sesión, copiar su Access Token Bearer y emitir una solicitud HTTP DELETE /api/messages/1 directa utilizando herramientas como curl, Postman o la propia consola de JavaScript mediante fetch().

Bajo el principio de Mediación Completa (Complete Mediation) y Defensa en Profundidad, la frontera de confianza (trust boundary) reside exclusivamente en el backend. La Web API está en la obligación inexcusable de interceptar la petición en el pipeline de autorización (.RequireAuthorization("delete:messages")) y retornar un código 403 Forbidden al constatar la ausencia del claim requerido.

Parte 3 · Investigación Técnica: Passkeys frente a TOTP

3.1 Fundamentos y Flujos de Funcionamiento

La autenticación de doble factor ha evolucionado desde mecanismos simétricos basados en tiempo hacia criptografía asimétrica de clave pública resistente a intermediarios (Man-in-the-Middle).

TOTP (RFC 6238): Se fundamenta en un secreto simétrico compartido $K$ entre el servidor y el cliente. Durante el enrolamiento, el servidor genera $K$ y lo transfiere al usuario mediante un código QR (URI otpauth://). En cada autenticación, ambos extremos calculan de forma desacoplada un contador de intervalos $T = \lfloor (T_{\text{actual}} - T_0) / 30 \rfloor$. El cliente genera un resumen evaluando $HS = \text{HMAC}(K, T)$ y aplica un truncamiento dinámico para extraer un código numérico de 6 dígitos. El usuario digita el código en la aplicación y el servidor replica el cómputo en una ventana de tolerancia $\pm 1$ para validar la autenticidad.

Passkeys (WebAuthn / FIDO2): Implementa un esquema asimétrico respaldado por el W3C y FIDO Alliance. En el registro, el servidor emite un desafío criptográfico (challenge) y el identificador de dominio (rp.id). El navegador invoca navigator.credentials.create() activando el autenticador local (Windows Hello, Touch ID o llave física). Este genera un par de claves asimétricas único para ese origen. La clave privada se resguarda dentro del hardware seguro (TPM / Secure Enclave) o sincronizada extremo a extremo. La clave pública se envía al servidor para asociarla a la cuenta. Durante el inicio de sesión, el servidor emite un nuevo challenge; el autenticador solicita validación biométrica o PIN, firma digitalmente el desafío junto con los datos de origen del cliente (clientDataJSON) utilizando la clave privada, y el servidor valida la firma con la clave pública registrada.

3.2 Resistencia a Phishing y Proxies Inversos

La vulnerabilidad crítica de TOTP radica en la ausencia de vinculación criptográfica con el canal o dominio. En ataques modernos con proxies inversos automatizados (Evilginx), un atacante clona la apariencia del portal en un dominio falso (ej. login-universidad.xyz). Cuando el usuario ingresa sus credenciales y el código de 6 dígitos, el proxy reenvía de inmediato estos datos al servidor legítimo dentro del margen de 30 segundos. El servidor genuino valida el código TOTP y expide la sesión al atacante, consumando el secuestro de la cuenta.

Por el contrario, las Passkeys son inmunes al phishing por diseño de protocolo. Durante la llamada a navigator.credentials.get(), el navegador extrae directamente de la barra de direcciones el dominio real y lo serializa en clientDataJSON.origin. Si el usuario ingresa a un sitio falso, el navegador solicita credenciales para dicho dominio fraudulento. Dado que la clave privada está ligada al dominio genuino, el autenticador no halla claves o firma el dominio falso. Al recibir la aserción, el servidor real detecta la discrepancia de origen y rechaza la solicitud. La clave privada jamás abandona el dispositivo del usuario.

3.3 Experiencia de Usuario y Migración de Dispositivos

En usabilidad, TOTP impone fricción cognitiva: requiere abrir una aplicación externa, memorizar 6 dígitos efímeros y transcribirlos manualmente. Si el estudiante cambia de teléfono sin exportar previamente la base de datos de su app autenticadora, pierde de forma irreversible sus accesos.

Las Passkeys ofrecen una interacción inmediata mediante autenticación biométrica (huella o reconocimiento facial). Gracias a la especificación de credenciales sincronizadas multi-dispositivo (respaldadas por Apple iCloud Keychain, Google Password Manager y Microsoft), las claves se sincronizan con cifrado de extremo a extremo. Al adquirir un teléfono nuevo, basta con ingresar a la cuenta principal del sistema operativo para disponer automáticamente de todas las passkeys.

3.4 Recuperación de Cuenta y Gestión de Riesgos

En TOTP tradicional, la recuperación depende de códigos de respaldo estáticos (frecuentemente extraviados por estudiantes) o en la intervención de mesas de ayuda, lo que genera saturación administrativa y riesgo de ataques de ingeniería social.

En Passkeys, la sincronización en la nube amortigua la pérdida del dispositivo. Para llaves físicas no sincronizadas (FIDO por hardware), WebAuthn fomenta enrolar múltiples autenticadores (laptop y smartphone). Adicionalmente, los proveedores de identidad complementan la recuperación mediante enlaces mágicos por correo institucional verificado o federación OpenID Connect.

3.5 Recomendación Técnica: Sistema Universitario de Calificaciones

Para una aplicación universitaria de consulta y registro de notas, se recomienda una estrategia híbrida basada prioritariamente en Passkeys con respaldo TOTP:

  1. Passkeys como método predeterminado: Brinda a la comunidad estudiantil y docente máxima protección contra phishing masivo en periodos de evaluaciones y agiliza el acceso en dispositivos personales sin fricción.
  2. Autenticación cruzada (FIDO Cross-Device): Al ingresar desde terminales compartidas de bibliotecas o laboratorios, el sistema despliega un código QR que el estudiante escanea con su celular personal, firmando la sesión localmente sin dejar credenciales guardadas en el equipo público.
  3. TOTP como alternativa secundaria: Permanece disponible como opción de contingencia para estudiantes con dispositivos heredados o navegadores que carezcan de soporte WebAuthn completo.

Conclusiones Personales

El desarrollo de esta práctica permitió comprender de manera integral la dualidad entre la implementación artesanal de mecanismos de autenticación y la adopción de proveedores de identidad federados como Auth0. La implementación de refresh tokens con rotación estricta y detección de reutilización en ASP.NET Core demostró cómo una arquitectura de tokens efímeros puede brindar una experiencia de usuario fluida sin comprometer la seguridad frente a robos de sesión. Asimismo, la confrontación técnica entre TOTP y Passkeys evidencia una transición ineludible en la industria del software: el abandono progresivo de secretos simétricos compartidos vulnerables a la ingeniería social en favor de la criptografía asimétrica vinculada al dominio. Por último, la aplicación de roles RBAC en Auth0 consolidó un principio fundamental de la ingeniería de software seguro: la interfaz de usuario puede adaptarse para enriquecer la usabilidad, pero la frontera de seguridad y la mediación de permisos deben recaer siempre, con riguroso escepticismo, en las políticas de autorización del servidor.
